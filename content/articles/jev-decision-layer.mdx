很多生产环境里的 LLM 代码都有一套固定仪式：写一段提示词，结尾是“只能回答以下之一：`billing`、`technical`、`sales`”；调用模型；去掉空白、转成小写，祈祷它别多附一句解释，真附了就退回默认值。有时还会加一次重试。有时会配上 JSON schema 和结构化输出模式，这能管住答案的形状，却几乎说明不了模型有多大把握。

这套仪式之所以存在，是因为生成式模型的原生输出是字符串，而软件在决策点上想从模型那里拿到的，大多不是字符串，而是一个分支。

Jev 正是从这种错位出发的。它由 TypeSafe AI 于 2026 年 9 月 15 日以抢先体验（early access）形式发布，不生成文本：你发给它一个状态（state）和一组带类型的问题，它返回附带概率的、带类型的答案。TypeSafe 称它为首个“系统一模型”（System One model），名字取自卡尼曼（Kahneman）所说的快速、直觉式的“系统一”（System 1）。Simon Willison 赞同 Maggie Appleton 的看法，更愿意叫它“决策模型”（decision model）——这个名字直接说明了它是干什么的。

本文从文档出发，由内向外解读 Jev。目的是把三类内容分开：TypeSafe 文档里写明的，TypeSafe 宣称的，以及据此作出的工程推断；然后再弄清楚这样一个模型在智能体（agent）里应该放在哪里。

## 实际交付了什么

除非另有说明，以下内容均来自 TypeSafe 文档，版本为 `jev-1.13.0`。

接口只有一个：`POST /v1/systemone`。请求包含 `state`、`model` 和一个 `questions` 映射。状态是文本：可以是字符串、JSON 对象，或文本值数组；不接受图像、音频和视频。每个问题有一个你自己定的 ID（模型永远看不到它）、一个 `type`、一段 `instructions`，通常还有 `criteria`。

JSON

```json
{
  "model": "jev-latest",
  "state": {
    "ticket": "I was charged twice for order A-104. Please refund the duplicate.",
    "refund_policy": "Duplicate charges are eligible for a refund."
  },
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle `ticket`?",
      "criteria": {
        "billing": "Charges, invoices, refunds",
        "orders": "Delivery, cancellation, returns",
        "account": "Login, profile, security"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "How frustrated does the customer appear in `ticket`?",
      "criteria": ["Calm and factual", "Frustrated but civil", "Very angry"]
    },
    "refund_requested": {
      "type": "noul",
      "instructions": "Does `ticket` explicitly request a refund or credit?"
    }
  }
}
```

> 译注：上面是接口请求示例，字符串内容属于传给模型的数据，故不翻译。大意为：工单内容“订单 A-104 被重复扣款两次，请退还重复的那笔”；退款政策“重复扣款可退款”。三个问题分别是：该由哪个团队处理（账务：扣款、发票、退款／订单：配送、取消、退货／账户：登录、资料、安全）；客户看起来有多恼火（平静陈述事实／恼火但还算客气／非常愤怒）；工单是否明确要求退款或抵扣。

响应在每个 ID 下给出一个答案。Choice（单选）返回 `choice`、覆盖全部选项的 `probabilities` 映射，以及 `confidence`。Score（定级）返回 `score`——它是沿各级别排列的一个位置，可以落在两级之间——外加 `probabilities`、`confidence` 和一个 `legend`。Noul（是非）只返回一个 `noul`：答案为“是”的概率。Noul 没有单独的置信度字段，因为这个概率本身就是不确定性。

每个问题看到的都是同一份状态，除此之外什么也看不到。任何答案都不会成为另一个问题的上下文，也不会落到代码定义的选项之外。这些值意味着什么、接下来做什么，由应用代码决定。

有几条约束决定了它的用法：

- Choice 最多支持 255 个选项；Score 支持 2 到 10 个有序级别。
- 同一请求中的问题针对同一份状态，彼此独立、并行求值。一个答案永远不会成为另一个答案的上下文。如果后一个问题确实依赖前一个答案，那就是第二次请求，由你的代码发起。
- `jev-1.13` 每次请求的 token 预算为 64k，其中状态加上最长的单个问题不得超过 32k。
- 主要训练语言是英语。其他语言也能用，但效果差一些。
- 不支持微调，所有账户共用同一套权重。要让 Jev 适应某个领域，只能靠状态、指令和判别标准（criteria）。
- `jev-latest` 是一个别名，新版本发布时会随之切换。模型页面建议：一旦你针对某个版本调好了阈值，就把版本固定下来。这条建议对任何模型都适用，对它则必不可少。

训练方法叫 RLCD，即“面向校准决策的强化学习”（Reinforcement Learning for Calibrated Decisions）。TypeSafe 把它与 RLHF、RLVR 并列，定位为第三种后训练目标，优化的是“认知上诚实的概率”，而不是人类偏好。这是 TypeSafe 自己的描述；本文没有找到可供对照的独立技术说明或评测。

## 设计上的压力：原子化问题

文档里重复最多的建议是：拆解。要问的是“一个懂行的人在掌握恰当上下文时，一秒钟就能作出的判断”。不要让 Jev“分析这条消息并确定最佳处理方式”，而要分别问：它是否要求退款？是否提到一笔未完成的订单？发信人有多恼火？再在代码里把这些答案组合起来。

这条建议源自架构本身。由于问题彼此独立、加一个的成本很低，十个窄问题的延迟和一个问题大致相当。由于每个答案都是附带概率的类型化值，组合它们只需一个加权和，或一条在代码评审里一眼看得懂的规则。“复合打分”这一模式把这一点说得很透：优先级变了，你改的是一个系数，而不是一段提示词。

文档还往前推了一步，提出“投机式扇出”（speculative fan-out）：把代码可能用到的问题全都问上，包括只在某些分支才有用的，再把无关的答案丢掉。比如在同一次调用里既给工单分诊，又给 bug 严重程度打分；如果最后发现是账务问题，就把严重程度扔掉。原语（primitives）页面引用了一个示例手册（cookbook）：把 13 个问题合并成一次调用，比分 13 次调用便宜 11.5 倍、快 9.6 倍；而该示例手册自己的总结给出的数字略有不同（12.2 倍和 10.0 倍）。具体倍数不如方向重要：在这个模型里，一次请求多问几个问题几乎不花钱。

隐藏的代价是：问题集本身变成了程序。总得有人决定，哪些原子判断加起来等于“这张工单该不该升级”；得写出能把选项干净区分开的判别标准，还得随着产品变化去维护它们。这是实打实的设计工作，更像传统机器学习里构建特征模型，而不是写提示词。Jev 把功夫从输出解析挪到了问题设计上。这通常是笔划算的交换，但活儿并没有消失。

## 把“置信度”说准确

置信度是 Jev 在架构上引人注目的关键特性，因此值得把这个数字到底是什么说准确。

对一个有 n 个选项的 Choice，置信度衡量的是最高概率比均匀分布高出多少，再缩放到 0–1：

```
confidence = (p_max − 1/n) / (1 − 1/n)
```

所有选项可能性相等时它为 0，全部概率集中在一个选项上时它为 1。只有最高概率参与计算，所以 (0.6, 0.3, 0.1) 和 (0.6, 0.2, 0.2) 的置信度都是 0.4。Score 的置信度用的是另一个考虑了顺序的公式：概率分散在相邻级别之间，对置信度的拉低要小于分散在两端之间。对于 Noul，如果你想要一个可比的数字，文档建议用 |2p − 1|。

由此可得两点。第一，置信度并不是模型给出的独立信号，而是从你已经拿到的同一个分布中算出来的统计量。文档对此毫不讳言，还建议了一些可能更适合特定决策的替代指标，比如最高概率本身，或前两名概率之比。第二，“校准”这一宣称针对的是概率，而且描述的是一批预测而非单个预测：被赋予 0.8 概率的结果，作为一个整体，应当有大约 80% 是对的，而其中任何一个都可能出错。`confidence` 字段是最高概率的缩放，本身并不是概率。置信度 0.8 并不意味着有 80% 的把握答对；在一个三选项的 Choice 上，它对应的最高概率约为 0.87。文档把这两个概念分得很清楚，设阈值时也应如此。

校准过的置信度之所以有用，在于它能让代码对同一个答案采取不同的动作。文档里的语音银行示例是：低于某个下限的一律转人工；置信度中等时可以显示余额；而对于转账，则要看一个高得多的阈值，决定是直接执行还是请用户确认。

模型报告它有多确定，代码决定这份确定在每个动作上值多少。同样的置信度，用来显示余额足够，用来转账却不够；而这些阈值要在你自己的标注数据上调出来，而不是凭信任照搬。

那个示例里的阈值只是举例。文档明说，合适的取值取决于你的领域和数据，应该从保守值起步，并在你自己的标注样本上把置信度与准确率画成曲线来看。换句话说，Jev 提供的是一个不确定性信号；在每个阈值上该信它几分，仍然是应用自己的事。

## 细读“不会幻觉”

发布文章说 Jev “不会幻觉”，并且从不犯类型错误。第二条在构造上就成立：输出空间就是你定义的选项集合，所以模型不可能返回 `"biling"`，也不可能返回一段道歉。发布文章自己也补充说明，它那个 0% 的数字“并非实测”，因为模式匹配是有保证的。

第一条则需要收窄。Jev 无法编造你选项之外的值，但它仍可能在选项之内选错，而且可能是满怀信心地选错，也可能不是。在日常用法里，“幻觉”同时涵盖两种情况：捏造内容，以及断言错误的事。Jev 在边界上消除了前一种；后一种，校准的作用是让它变得可见，而不是让它不可能发生。

TypeSafe 自己的示例手册，比发布文案更好地讲清了这个区别。结构化数据抽取级联（extraction cascade）那份手册里有一句话：“模式校验必要但不充分：它能抓住结构错误，却永远抓不住语义错误。”自洽性（self-consistency）示例手册则拿一条处于边界的待审核帖子，跑八个 Choice 问题，每种条件重复十五次。Jev 有 90.8% 的时候会重复给出其多数标签，落在所测 LLM 配置 87.5% 到 100% 的区间内；其概率的波动小于六种 LLM 条件中的五种。但在 8 个问题中，仍有 2 个出现了标签翻转。手册给出的补救办法是：设置最高概率下限 0.60，低于它就明确输出 `uncertain`，交由人工审核。加上这道门槛后，Jev 的一致率升至 99.2%，同时仍有 74.2% 的答案能够自动打标。一条帖子、十五次重复，是个很小的实验；它更多是在演示这套机制，而不是在衡量这个模型。

公允的解读是：Jev 让决策变得类型良好、可以检查，并给了代码一个“何时不该信它”的信号。正确性仍然来自好的问题、好的状态，以及把低置信度答案当作“未知”来处理的代码。

## 它在哪里会失灵：开发者自己的说法

TypeSafe 为 `jev-1.13` 发布了一个“能力参差”（jaggedness）页面，最近一次审阅是在 2026 年 10 月 2 日。对于要决定是否依赖这个模型的工程师来说，这是文档里更有用的页面之一，而且说得很直白：

- 字面理解。它回答的是你写下的问题，而不是你想问的问题。否定和隐含条件都按字面处理。
- 数学与数字。它数数不可靠，处理十六进制颜色这类数值表示很差；也不应拿 Score 的位置去插值推算精确的量级。
- 日期。它把日期当文本读，而不是当有序的量。应当把日期的各部分作为 Choice 抽取出来，再在代码里比较。
- 间接表达。双重否定和多跳问题会降低准确率。
- 庞大而无关的状态。无关内容越多，准确率越低。先过滤。
- 对抗性内容。默认情况下，它不把状态视为敌意内容。注入的指令，或为自己的分类结果“辩护”的文本，“可能会让答案偏移”。
- 相互矛盾的判别标准，以及选项顺序：在 Choice 中它可能偏向第一个选项。
- 生成。它没有被训练来产出文本，靠串联 Choice 来假装生成，既慢又差。

其中有些属于寻常的工程常识（算术留在代码里）。有两点对构建智能体的人更要紧。

对抗性这一点意味着，Jev 本身并不是提示词注入的防线。一个读取不可信内容的 Jev 护栏，和任何读取不可信内容的模型一样，承受着同样的压力。它也许便宜到足以对每条消息都跑一遍，攻击者也没法让它写出有害文本，因为它根本不写文本。但一段措辞巧妙的输入仍然能让某个概率偏移，所以基于 Jev 的护栏和其他护栏一样，需要做对抗测试。

字面理解这一点意味着，问题的措辞比初看起来更要紧。当 Jev 的某个决策出错，而你发现自己正在解释“我本来的意思是……”，文档的建议是：这段解释，正是指令里缺失的另一半。这是好建议，但它也是一项随问题数量增长的维护负担。

## 各项宣称，以及它们能承受多少分量

速度和成本是 TypeSafe 自家页面上的头条数字。下面列出一手来源怎么说，以及 TypeSafe 附带的限定说明。凡属本文解读而非 TypeSafe 原话的限定，均已标注。

| 宣称 | 来源 | 限定说明 |
| --- | --- | --- |
| 每百万输入 token 0.042 美元；输出 token 免费 | 模型页面、发布文章 | 发布文章：“我们无法证明它没有补贴。” |
| 端到端 70–500 毫秒；“大多数查询约 100 毫秒完成” | 发布文章；《How to build》指南 | 评测“一般”是在团队位于美国西海岸的笔记本电脑上运行的，而服务本身也部署在那里。 |
| 快 193.6 倍，便宜 444.6 倍 | 发布文章，工作流评测 | TypeSafe 预计这些数字“处于真实收益的偏高一端”。工作流由其自家团队搭建；参考答案是两个前沿 LLM 答案的平均。 |
| 在“系统一”类任务上智能水平与 LLM 相当 | 发布文章 | 工作流评测对照的是 LLM 给出的参考答案，而非真实标注（ground truth）。本文解读：该文并未把这一头条宣称与某项具体评测对应起来。 |
| 类型错误率 0% | 发布文章 | 由构造保证，并非实测。 |
| 每秒 10 万 token，每秒 80 次请求 | 模型页面 | 限额“正在动态调整”，可能不另行通知即变更。 |

这些数字全部来自 TypeSafe，本文的论证也都不依赖对它们的独立基准测试。定价是公开的，有访问权限的人都可以从自己所在的位置测一测延迟。最需要审慎对待的是智能水平的对比，因为它是相对于其他模型在 TypeSafe 自选工作流上的答案来定义的。TypeSafe 对这一切都很坦诚，这值得肯定；而每当有人引用这些倍数时，限定说明也应当一并附上。

## 文档怎么谈智能体——这才是有意思的地方

《How to build》指南里有一句话，让其他所有内容都换了一个角度来看：“System One 是 TypeSafe 用来构建 AI 驱动软件的模型，而不是用来构建智能体的。它不生成代码，也不自行选择下一步动作。”指南对比了三种架构：传统软件；LLM 智能体（“每一轮循环都多了一次跑偏的机会”）；以及 AI 驱动软件——由代码掌控控制流，模型只做狭窄、受约束的判断。它建议：只要一个工作流能表达同样的行为，就避免使用智能体式的 `while` 循环。

所以，厂商自己的立场并不是“用 Jev 来构建智能体”，更接近于“用 Jev 来少用智能体”。这是针对智能体难点之一的一种自洽立场：在智能体里，模型每一步都要就控制流作出开放式决策，每一次都是一个出错的机会。决策模型提供了一条路：在这些节点上保留模型的判断，而控制流仍由代码掌握。

在实践中，智能体与 AI 驱动软件并非二选一。一个真实的智能体就是一个循环，里面装着许多小决策，而其中大多数并不是开放式的。该由哪个专家处理？检索到的段落相关吗？草稿是否引用了来源中并未出现的内容？这个动作风险高到需要人来把关吗？每一个都是有界问题，答案空间都能写下来。在完全围绕 LLM 构建的智能体里，这些问题全都经由同一个生成式模型处理，以文本或工具调用的形式。

这正是 Jev 的位置：不是智能体的大脑，而是嵌在其中的决策层。

## 它在智能体里的位置

文档中的模式和示例手册覆盖了智能体的若干决策点。在每一种情况下，都是 Jev 回答一个有界问题，代码根据答案行动。

- 路由。对意图和复杂度分类，然后把请求交给确定性代码、某个专精 LLM 或人工（意图路由）。
- 工具与技能选择。技能推荐示例手册针对一轮用户输入，对 182 个智能体技能（skill）排序，再用更完整的描述复核前三名，并且允许全部否决。TypeSafe 报告称，这让错误加载技能的情况减少了一半以上。函数调用示例手册则把一个请求映射到函数名和封闭集合内的参数上，每一项都作为一个 Choice 来回答，各带自己的置信度。
- 模型间升级。抽取级联先用一个便宜的 LLM，再对每个字段用 Jev 的 Noul 询问是否有异样，只有标记被触发时才动用推理模型。这是“由校验触发的升级”；该示例手册并没有用 Jev 来事先挑选模型。（它运行的还是 `jev-1.12`。）
- 护栏。每条消息一次请求，进出各一次：每种危害一个 Noul，严重程度一个 Score，在代码里按阈值决定放行、复审、拦截或转送（LLM 护栏）。
- 校验。引用核查示例手册先做一次朴素的字符串匹配，抓出捏造的引文；再用一个 Choice 询问上下文段落对该论断是支持、反驳还是未曾提及；凡低于置信度阈值的，一律交给人。
- 兜底。这些模式大多为“不确定”或“被标记”的答案准备了一条分支。在意图路由、护栏和引用核查里，它的终点是人；在级联里，是更强的模型；在技能推荐里，则是不加载任何技能。

下面是一个示意性设计，并非 TypeSafe 的示例：一个客服智能体处理退款请求的一轮交互，把上面这些部件组合在一起。

LLM 是唯一负责写的部分。Jev 回答关于请求和关于草稿的窄问题。代码掌控每一次状态转换和每一个副作用。人只会看到被置信度门槛或策略限额转过来的那些案例。

代码构建状态：工单、订单记录、退款政策。第一次 Jev 请求对请求分类，并问一组筛查问题。代码执行门槛判断。在自动路径上，由 LLM 起草回复并提出退款方案——这是需要生成能力的部分。第二次 Jev 请求对照状态检查草稿。代码执行限额，并通过一个幂等调用完成退款。凡是不确定、被标记，或金额超出自动处理范围的，都交给人。

TypeScript

```typescript
const screen = await systemOne({ state, questions: screeningQuestions });
const team = screen.answers.team;

if (team.confidence < THRESHOLDS.route) return toHuman('unclear request');
if (screen.answers.injection_attempt.noul > THRESHOLDS.injection)
  return toHuman('suspicious');
if (team.choice !== 'billing') return handOff(team.choice);

// LLM 只负责提议，不负责执行。
const draft = await llm.draftReply({ ticket, order, policy });

const check = await systemOne({
  state: { ticket, order, policy, draft: draft.text, proposed: draft.action },
  questions: draftChecks, // grounded_in_order（有订单依据）、within_policy（符合政策）、promises_beyond_policy（承诺超出政策）
});

// 两项检查是“是”为好，一项是“是”即有问题。
const draftOk = ['grounded_in_order', 'within_policy'].every(
  id => check.answers[id].noul >= THRESHOLDS.check
);
const overPromises =
  check.answers.promises_beyond_policy.noul >= THRESHOLDS.flag;

const amount = order.charges.at(-1)?.amountUsd ?? 0; // 金额由代码读取，绝不交给模型
const amountOk = amount > 0 && amount <= LIMITS.autoRefundUsd;

if (!draftOk || overPromises || !amountOk)
  return toHuman('review draft', { draft, check });

await refunds.issue({
  orderId: order.id,
  amount,
  idempotencyKey: `refund:${order.id}`,
});
return send(draft.text);
```

这里的 `systemOne` 只是对文档所述接口的一层薄封装；阈值和限额都是占位符，实际取值要在真实数据上调出来。每个草稿检查问题都“问什么就是什么”，所以 `promises_beyond_policy` 得到“是”，在代码里被当作问题来读，而不是在问题内部把意思反过来；能力参差页面指出，“真”对应“否”的 Noul 表现更差。还要注意代码没有问 Jev 什么：退款金额。金额由代码从订单记录里读取。数字本就在能力参差清单上；况且，记录里已有的金额，本来就该从记录里取。

## 不该用它的地方

第一、四、五条直接来自文档。其余几条则是结合文档，从工程角度判断这种架构在哪里不再合适。

- 任何需要生成输出的场景：回复、代码、摘要、计划、解释。文档说得很明确：用生成式模型。
- 开放的答案空间。如果你无法穷举选项，或者选项随每次请求变化、而你又无法在代码里把它们构造出来，Choice 就不合适。文档中的抽取模式绕开这一点的办法是：让正则表达式或 LLM 提出候选，再由 Jev 从中挑选；候选容易生成时，这招管用。
- 需要给出明确理由的决策。Jev 返回的是概率，不是理由。如果监管方、客户或事故复盘需要知道“为什么”，理由就得来自别处，或者来自拆解本身（原子问题和权重就是解释）。
- 在单个问题里做多步推理。按设计，这类推理应当拆成多个问题或多次请求。如果一个决策无法拆解，它多半是“系统二”（System 2）的任务，应交给推理模型。
- 数字、日期和计数，这些归代码管。
- 未经测试的语言和领域。英语上准确率最高。在一种数据分布上测得的校准，不会自动迁移到另一种分布上。

还有一些取舍来自产品，而非模型。Jev 出自一家年轻公司，尚处抢先体验阶段，限流规则可能不另行通知即变更。它是托管的黑盒，没有微调途径，所以模型本身只能随新版本发布而改进。不过，正如文档所述，你自己的数据仍然可以用来塑造状态和问题，或者用 Jev 的输出去训练一个下游的传统模型。别名会切换，所以除非固定版本，一次版本升级就可能改变一个已校准系统的行为。对一个新的模型 API 来说，这些都不稀奇；但在决定是否把它放上关键路径时，这些都该纳入考量。

## 为什么“Jev 取代 LLM”没抓住要点

人们很容易把 Jev 理解为生产环境中 LLM 的替代品。TypeSafe 自己的文档并没有这么说。编程智能体页面明确指出，Jev 不能直接替换编程智能体背后的模型；能力参差页面也把生成任务交还给了“其他模型”。

Jev 能取代的，是 LLM 的一种特定用法：被当作一个昂贵、缓慢、输出还难以解析的分类器。智能体周边的大量基础设施正是这个样子：决定用哪段提示词的路由器；判断答案是否有依据的评判器；每条消息都要跑的安全检查；循环末尾那个“任务做完了吗？”的检查。其中很多之所以架在生成式模型上，是因为它是手边最方便的通用工具：不需要训练数据，也不需要另外部署一个模型。如果有一个决策模型能把这些活儿干得更快、更便宜，还附带可用的置信度信号，LLM 的用途就会收窄，集中到真正需要生成和长链推理的地方。

由此可以得出一种分工：

- LLM 负责提议、推理、规划和写作，处理开放式的工作。
- Jev 回答有界问题：哪一个、多少、是否。它处理答案空间已知的决策。
- 代码掌控控制流、执行规则、做算术、产生副作用。
- 人处理被门槛标为不确定或影响重大的情况。

这种分工有用，也有例外。有些路由决策更适合交给 LLM，因为类别模糊且经常变化。有些更适合用普通代码，因为一个关键词或一个数据库字段就已经给出了答案，根本不需要模型。有些决策无论置信度多高都应交给人，因为“自信地犯错”的代价太大，不宜自动化。此外，Jev 的置信度好不好用，全看它在你的数据上校准得如何，而这一点你必须先测量，才能信任。

## 这对可靠的智能体意味着什么

除了速度和价格，Jev 还带着一个关于“可靠性从何而来”的论点。完全围绕生成式模型构建的智能体，每跑一次都要做许多小决策，用的就是它写文章的那个模型。即便有结构化输出，这些决策通常也不带经过校准的置信度信号，而且和模型正在做的其他事情混在一起。

决策层把这些决策拆了出来。每个决策都变成一个有名字的问题，有明确的答案空间，在专门构建的状态上求值，返回一个代码可以设阈值、记日志、并用标注样本来测试的数字。模型并没有因此变得更聪明，但智能体的行为变得更容易检查了，因为“没有人决定交出控制权、控制权却被交给了模型”的地方变少了。

Jev 本身能否成为这样的决策层，取决于文档目前还无法回答的几件事：独立评测、对抗性输入下的表现、价格是否稳定，以及校准在 TypeSafe 自家工作流之外能保持多好。而这种架构模式并不依赖 Jev。有界的问题、类型化的答案、显式的置信度，再加上由代码承担后果——无论用哪种模型，这都是构建智能体的好方法。
