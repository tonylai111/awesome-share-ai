译自 [Akshay Shinde](https://akshayshinde.com/blog/jev-and-the-decision-layer)，2026 年 10 月 8 日，原文大约 19 分钟。他的页面只有一张用来社交分享的封面，正文里没有插图。Choice、Score、Noul 是接口里的类型名，下面保留英文。

这篇顺着文档，把 TypeSafe AI 的 Jev 读一遍。你给它一份状态，再给一组带类型的问题，它返回校准过的 Choice、Score 和 Noul。哪些写在文档里，哪些只是厂商的说法。它适合放在智能体的哪里，不适合放在哪里。以及它为什么是在补大模型，而不是换掉大模型。

很多生产环境里的大模型代码，都有一套固定仪式。提示词结尾写着，只能从 `billing`、`technical`、`sales` 里挑一个。然后调用模型，去掉空白，转成小写，指望它别再多解释一句。真多了一句，就退回默认值。有的人会再试一次。有的人配了 JSON schema 和结构化输出。答案的形状被管住了。模型有多大把握，几乎还是不知道。

这套仪式存在，是因为生成式模型吐出来的是字符串。软件在决策点上想要的，通常不是字符串，而是一个分支。

Jev 就从这里出发。TypeSafe AI 在 2026 年 9 月 15 日以抢先体验发布了它。它不生成文本。你给它一份状态，再给一组带类型的问题，它返回带概率的类型化答案。TypeSafe 称它是第一个系统一模型。这个名字来自卡尼曼说的那种快而直觉的系统一。Simon Willison 同意 Maggie Appleton 的叫法，更愿意称它为决策模型。这个名字直接说明它是干什么的。

本文从文档往外读。先分开三件事。文档写明了什么。TypeSafe 宣称了什么。据此又能做哪些工程推断。然后再看，这样的模型该放在智能体的哪里。

## 实际交付了什么

除非另有说明，下面都来自 TypeSafe 文档，版本是 `jev-1.13.0`。

接口只有一个，`POST /v1/systemone`。请求里有 `state`、`model`，以及一个 `questions` 映射。状态是文本。可以是字符串，可以是 JSON 对象，也可以是一组文本。图像、音频和视频都不收。每个问题有你自己定的 ID，模型永远看不到这个 ID。还有一个 `type`，一段 `instructions`，通常再加 `criteria`。

请求长这样。引号里的英文是交给模型的原文，不翻译。工单写的是订单 A-104 被扣了两次款，请退掉重复的那一笔。退款政策写的是重复扣款可以退。三个问题分别问，该哪个团队处理，客户看起来有多恼火，以及工单有没有明确要求退款或抵扣。团队选项是账务、订单和账户。账务看扣款、发票和退款。订单看配送、取消和退货。账户看登录、资料和安全。恼火程度从平静陈述事实，到恼火但还算客气，再到非常愤怒。

```json
{
  "model": "jev-latest",
  "state": {
    "ticket": "I was charged twice for order A-104. Please refund the duplicate.",
    "refund_policy": "Duplicate charges are eligible for a refund."
  },
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle `ticket`?",
      "criteria": {
        "billing": "Charges, invoices, refunds",
        "orders": "Delivery, cancellation, returns",
        "account": "Login, profile, security"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "How frustrated does the customer appear in `ticket`?",
      "criteria": ["Calm and factual", "Frustrated but civil", "Very angry"]
    },
    "refund_requested": {
      "type": "noul",
      "instructions": "Does `ticket` explicitly request a refund or credit?"
    }
  }
}
```

响应按你给的 ID，逐条返回答案。Choice 返回选中的 `choice`，一份覆盖全部选项的 `probabilities`，以及 `confidence`。Score 返回一个 `score`。它是沿着各级别排开的位置，可以落在两级之间。另外还有 `probabilities`、`confidence` 和一个 `legend`。Noul 只返回一个 `noul`，也就是答案为「是」的概率。Noul 没有单独的置信度字段，因为这个概率本身就是不确定性。

每个问题只看见同一份状态，别的什么都看不见。任何一个答案，都不会变成另一个问题的上下文，也不会落到代码定义的选项之外。这些值是什么意思，接下来做什么，由应用代码决定。

用法上有几条硬约束。

Choice 最多 255 个选项。Score 是 2 到 10 个有序级别。

同一次请求里的问题，对着同一份状态，彼此独立，并行计算。一个答案永远不会成为另一个答案的上下文。后一个问题如果真的依赖前一个答案，那就再发一次请求，由你的代码发起。

`jev-1.13` 每次请求的 token 预算是 64k。其中状态加上最长的那一个问题，不得超过 32k。

主要训练语言是英语。别的语言也能用，效果差一些。

不支持微调。所有账户共用同一套权重。想让它适应某个领域，只能靠状态、指令和判别标准。

`jev-latest` 是个别名。新版本一发布，它就跟着切过去。模型页面建议，一旦你对着某个版本调好了阈值，就把版本固定下来。这条建议对任何模型都适用。对它，则必不可少。

训练方法叫 RLCD，全称是面向校准决策的强化学习，英文是 Reinforcement Learning for Calibrated Decisions。TypeSafe 把它和 RLHF、RLVR 并列，当作第三种后训练目标。它优化的是「认知上诚实的概率」，而不是人类偏好。这是 TypeSafe 自己的描述。本文没有找到可以对照的独立技术说明，也没有找到独立评测。

## 把问题拆开

文档里重复最多的建议，是拆开。要问的是「一个懂行的人，手里有合适的上下文，一秒钟就能作出的判断」。不要让 Jev「分析这条消息，并确定最佳处理方式」。分开问。它要不要退款。它有没有提到一笔还没完成的订单。发信人有多恼火。再在代码里把这些答案合起来。

这条建议来自架构本身。问题彼此独立，多加一个也便宜。十个窄问题的延迟，和一个问题大致相当。每个答案都是带概率的类型化值，组合它们只需要一个加权和，或者一条在代码评审里一眼看得懂的规则。他们称为复合打分的那种写法，把这一点说得很透。优先级变了，你改的是一个系数，不是一段提示词。

文档还往前推了一步，管这个叫投机式扇出，英文是 speculative fan-out。代码可能用到的问题，全部问上，包括只在某些分支才用得着的。用不上的答案扔掉。比如同一次调用里，既给工单分诊，又给 bug 的严重程度打分。最后发现是账务问题，就把严重程度扔掉。文档里讲基本类型的 primitives 页面，引用了一份示例手册。把 13 个问题并成一次调用，比拆成 13 次调用便宜 11.5 倍，快 9.6 倍。那份手册自己的总结，数字略有不同，是 12.2 倍和 10.0 倍。具体倍数不如方向重要。在这个模型里，一次请求多问几个问题，几乎不花钱。

藏起来的代价是，问题集本身变成了程序。总得有人决定，哪些小判断加起来，才等于「这张工单该不该升级」。还得写出能把选项干净分开的判别标准，并跟着产品变化去维护。这是实打实的设计工作，更像传统机器学习里构建特征模型，而不是写提示词。Jev 把功夫从解析输出，挪到了设计问题上。这通常是笔划算的交换。活儿并没有消失。

## 把置信度说准确

置信度是 Jev 在架构上最值得看的特性，所以这个数字到底是什么，值得说准确。

对一个有 n 个选项的 Choice，置信度衡量的是最高概率比均匀分布高出多少，再缩放到 0 到 1。

```
confidence = (p_max − 1/n) / (1 − 1/n)
```

所有选项一样可能时，它是 0。全部概率集中在一个选项上时，它是 1。只有最高概率参与计算。所以 (0.6, 0.3, 0.1) 和 (0.6, 0.2, 0.2) 的置信度都是 0.4。Score 的置信度用另一套考虑了顺序的公式。概率散在相邻级别之间，对置信度的拉低，要小于散在两端之间。对于 Noul，如果你想要一个可以比较的数字，文档建议用 |2p − 1|。

由此有两点。

第一，置信度不是模型另外给的信号。它是从你已经拿到的同一个分布里算出来的统计量。文档对此说得很直，还建议了一些可能更适合某个决策的替代指标，比如最高概率本身，或者前两名概率之比。

第二，「校准」说的是概率，而且说的是一批预测，不是单条预测。被赋予 0.8 概率的结果，作为一个整体，应当有大约 80% 是对的。其中任何一条，都可能是错的。`confidence` 字段是最高概率的缩放，本身并不是概率。置信度 0.8 并不意味着有 80% 的把握答对。在一个三选项的 Choice 上，它对应的最高概率大约是 0.87。文档把这两个概念分得很清楚。设阈值的时候，也该这样分。

校准过的置信度有用，是因为它能让代码对同一个答案采取不同动作。文档里的语音银行示例是这样的。低于某个下限的，一律转人工。置信度中等时，可以显示余额。转账则要看一个高得多的阈值，决定是直接执行，还是请用户确认。

模型报告它有多确定。代码决定这份确定在每个动作上值多少。同样的置信度，用来显示余额够了，用来转账却不够。这些阈值要在你自己的标注数据上调出来，不能凭信任照搬。

那个示例里的阈值只是举例。文档写明，合适的取值取决于你的领域和数据。应该从保守值起步，并在你自己的标注样本上，把置信度和准确率画成曲线来看。换句话说，Jev 提供的是一个不确定性信号。在每个阈值上该信它几分，仍然是应用自己的事。

## 「不会幻觉」，要拆开看

发布文章说 Jev「不会幻觉」，并且从不犯类型错误。第二条在构造上就成立。输出空间就是你定义的选项集合，所以模型不可能返回 `"biling"`，也不可能返回一段道歉。发布文章自己也补了一句。它那个 0% 的数字「并非实测」，因为模式匹配是有保证的。

第一条则需要收窄。Jev 无法编造你选项之外的值。它仍可能在选项之内选错，而且可能是满怀信心地选错，也可能不是。日常说的幻觉，同时包括两种情况。一种是捏造内容。一种是把错的事说成对的。Jev 在边界上消除了前一种。后一种，校准的作用是让它变得看得见，而不是让它不可能发生。

TypeSafe 自己的示例手册，比发布文案把这个区别讲得更清楚。结构化数据抽取的级联手册里有一句话。「模式校验必要，但并不充分。它抓得住结构错误，永远抓不住语义错误。」讲自洽性的那份手册，拿一条处在边界上的待审核帖子，跑八个 Choice 问题，每种条件重复十五次。Jev 有 90.8% 的时候会重复给出它的多数标签，落在所测大模型配置 87.5% 到 100% 的区间里。它的概率波动，小于六种大模型条件中的五种。但在 8 个问题里，仍有 2 个出现了标签翻转。手册给出的补救是，设置最高概率下限 0.60。低于它，就明确输出 `uncertain`，交给人工审核。加上这道门槛之后，Jev 的一致率升到 99.2%，同时仍有 74.2% 的答案能够自动打标。一条帖子，十五次重复，是个很小的实验。它更多是在演示这套机制，而不是在衡量这个模型。

公允的读法是，Jev 让决策变得类型清楚、可以检查，并给了代码一个信号，告诉它什么时候不该信。正确性仍然来自好的问题、好的状态，以及把低置信度答案当成「未知」来处理的代码。

## 它会在哪里失灵

TypeSafe 为 `jev-1.13` 发布了一个能力参差页面，英文标题是 jaggedness，最近一次审阅是在 2026 年 10 月 2 日。对要决定是否依赖这个模型的工程师来说，这是文档里更有用的页面之一，而且说得很直白。

| 会失灵的地方 | 文档怎么说 |
| --- | --- |
| 字面理解 | 它回答的是你写下的问题，不是你心里想问的问题。否定和隐含条件，都按字面处理。 |
| 数学和数字 | 数数不可靠。十六进制颜色这类数值表示，它处理得很差。也不该拿 Score 的位置去插值，推算精确的量级。 |
| 日期 | 它把日期当文本读，不当成有序的量。应当把日期的各部分作为 Choice 抽出来，再在代码里比较。 |
| 间接表达 | 双重否定和多跳问题，会降低准确率。 |
| 又大又无关的状态 | 无关内容越多，准确率越低。先过滤。 |
| 对抗性内容 | 默认不把状态当成敌意内容。注入的指令，或者为自己的分类结果辩护的文本，「可能会让答案偏移」。 |
| 判别标准和选项顺序 | 判别标准互相矛盾时会出问题。Choice 里，它可能偏向第一个选项。 |
| 生成 | 它没有被训练来产出文本。靠串联 Choice 来假装生成，又慢又差。 |

其中有些就是寻常的工程常识，比如算术留在代码里。有两点对构建智能体的人更要紧。

对抗性这一点意味着，Jev 本身并不是提示词注入的防线。一个读取不可信内容的 Jev 护栏，和任何读取不可信内容的模型一样，承受着同样的压力。它也许便宜到足以对每条消息都跑一遍。攻击者也没法让它写出有害文本，因为它根本不写文本。但一段措辞巧妙的输入，仍然能让某个概率偏移。所以基于 Jev 的护栏，和其他护栏一样，需要做对抗测试。

字面理解这一点意味着，问题怎么写，比乍看之下更要紧。某个决策出错时，如果你发现自己正在解释「我本来的意思是……」，文档的建议是，这段解释正是指令里缺的另一半。这是好建议。它也是一项随问题数量增长的维护负担。

## 这些宣称，各能承受多少

速度和成本，是 TypeSafe 自家页面上的头条数字。下面列出一手来源怎么说，以及 TypeSafe 附带的限定。凡是本文的解读、不是 TypeSafe 原话的限定，都标了出来。

| 宣称 | 来源 | 限定 |
| --- | --- | --- |
| 每百万输入 token 0.042 美元。输出 token 免费 | 模型页面，发布文章 | 发布文章说，「我们无法证明它没有补贴。」 |
| 端到端 70 到 500 毫秒。「大多数查询大约 100 毫秒完成」 | 发布文章，《How to build》指南 | 评测「一般」是在团队位于美国西海岸的笔记本电脑上跑的。服务本身也部署在那里 |
| 快 193.6 倍，便宜 444.6 倍 | 发布文章，工作流评测 | TypeSafe 预计这些数字「处于真实收益的偏高一端」。工作流是它自家团队搭的。参考答案是两个前沿大模型答案的平均 |
| 在系统一类任务上，智能水平和大模型相当 | 发布文章 | 工作流评测对照的是大模型给出的参考答案，不是真实标注。本文的解读是，这篇文章并没有把这条头条宣称，对应到某一次具体评测上 |
| 类型错误率 0% | 发布文章 | 由构造保证，并非实测 |
| 每秒 10 万 token，每秒 80 次请求 | 模型页面 | 限额「正在动态调整」，可能不另行通知就变更 |

这些数字全部来自 TypeSafe。本文后面的讨论，也不依赖对它们的独立基准测试。定价是公开的。有访问权限的人，都可以从自己所在的位置测一测延迟。最需要审慎对待的，是智能水平的对比。它是相对于其他模型、在 TypeSafe 自己选定的工作流上的答案来定义的。TypeSafe 把这些都写在明面上，这点应该记一笔。别人引用这些倍数的时候，限定也该跟着走。

## 文档怎么谈智能体

《How to build》指南里有一句话，让前面这些内容换了一个角度看。「System One 是 TypeSafe 用来构建 AI 驱动软件的模型，不是用来构建智能体的。它不生成代码，也不自行选择下一步动作。」指南对比了三种架构。传统软件。大模型智能体，「每一轮循环，都多一次跑偏的机会」。以及 AI 驱动的软件。控制流由代码掌握，模型只做狭窄的、受约束的判断。它建议，只要一个工作流能表达同样的行为，就不要用智能体那种 `while` 循环。

所以，厂商自己的立场并不是「用 Jev 来构建智能体」。更接近「用 Jev 来少用智能体」。这是针对智能体难点之一的一种说得通的立场。在智能体里，模型每一步都要对控制流做开放式决策，每一次都是一个出错的机会。决策模型提供了另一条路。这些节点上仍保留模型的判断，控制流仍由代码掌握。

实践里，智能体和 AI 驱动的软件并不是二选一。一个真实的智能体就是一个循环，里面装着许多小决策，其中大多数并不是开放式的。该由哪个专家处理。检索到的段落相关吗。草稿有没有引用来源里根本没出现的内容。这个动作的风险，高到需要人来把关吗。每一个都是有界问题，答案空间都能写下来。在完全围绕大模型构建的智能体里，这些问题全都经过同一个生成式模型，以文本或工具调用的形式。

这正是 Jev 的位置。它不是智能体的大脑，而是嵌在里面的决策层。

## 它在智能体里放哪里

文档中的模式和示例手册，覆盖了智能体的若干决策点。每一种情况下，都是 Jev 回答一个有界问题，代码根据答案行动。

| 位置 | 怎么用 |
| --- | --- |
| 路由 | 对意图和复杂度分类，然后把请求交给确定性代码、某个专精的大模型，或者人工。文档里叫意图路由。 |
| 工具和技能 | 技能推荐的示例手册，针对一轮用户输入，给 182 个智能体技能排序，再用更完整的描述复核前三名，并且允许全部否决。TypeSafe 报告，这让错误加载技能的情况减少了一半以上。函数调用的示例手册，则把一个请求映射到函数名，以及封闭集合内的参数上。每一项都作为一个 Choice 来回答，各带自己的置信度。 |
| 模型之间的升级 | 抽取级联先用一个便宜的大模型，再对每个字段用 Jev 的 Noul 问有没有异样。只有标记被触发时，才动用推理模型。这是由校验触发的升级。这份手册并没有用 Jev 来事先挑选模型。它跑的还是 `jev-1.12`。 |
| 护栏 | 每条消息一次请求，进和出各一次。每种危害一个 Noul，严重程度一个 Score。代码按阈值决定放行、复审、拦截或转送。文档里叫大模型护栏。 |
| 校验 | 引用核查的示例手册，先做一次朴素的字符串匹配，抓住捏造的引文。再用一个 Choice 问，上下文段落对这个论断是支持、反驳，还是根本没提到。低于置信度阈值的，一律交给人。 |
| 兜底 | 这些模式大多为「不确定」或「被标记」的答案准备了一条分支。意图路由、护栏和引用核查里，终点是人。级联里，终点是更强的模型。技能推荐里，终点是不加载任何技能。 |

下面是一个示意性设计，不是 TypeSafe 的示例。一个客服智能体处理退款请求的一轮交互，把上面这些部件合在一起。

大模型是唯一负责写的部分。Jev 回答关于请求的窄问题，也回答关于草稿的窄问题。代码掌握每一次状态转换，以及每一个副作用。人只会看到被置信度门槛或策略限额转过来的那些案例。

代码先构建状态，包括工单、订单记录和退款政策。第一次 Jev 请求对请求分类，并问一组筛查问题。代码执行门槛判断。走自动路径时，由大模型起草回复，并提出退款方案。这是需要生成能力的部分。第二次 Jev 请求对照状态检查草稿。代码执行限额，并通过一个幂等调用完成退款。凡是不确定的、被标记的，或者金额超出自动处理范围的，都交给人。

```typescript
const screen = await systemOne({ state, questions: screeningQuestions });
const team = screen.answers.team;

if (team.confidence < THRESHOLDS.route) return toHuman('unclear request');
if (screen.answers.injection_attempt.noul > THRESHOLDS.injection)
  return toHuman('suspicious');
if (team.choice !== 'billing') return handOff(team.choice);

// 大模型只负责提议，不负责执行。
const draft = await llm.draftReply({ ticket, order, policy });

const check = await systemOne({
  state: { ticket, order, policy, draft: draft.text, proposed: draft.action },
  questions: draftChecks, // grounded_in_order（有订单依据）、within_policy（符合政策）、promises_beyond_policy（承诺超出政策）
});

// 两项检查是「是」为好，一项是「是」即有问题。
const draftOk = ['grounded_in_order', 'within_policy'].every(
  id => check.answers[id].noul >= THRESHOLDS.check
);
const overPromises =
  check.answers.promises_beyond_policy.noul >= THRESHOLDS.flag;

const amount = order.charges.at(-1)?.amountUsd ?? 0; // 金额由代码读取，绝不交给模型
const amountOk = amount > 0 && amount <= LIMITS.autoRefundUsd;

if (!draftOk || overPromises || !amountOk)
  return toHuman('review draft', { draft, check });

await refunds.issue({
  orderId: order.id,
  amount,
  idempotencyKey: `refund:${order.id}`,
});
return send(draft.text);
```

这里的 `systemOne` 只是对文档所述接口的一层薄封装。阈值和限额都是占位符，实际取值要在真实数据上调出来。每个草稿检查问题都是问什么就是什么。所以 `promises_beyond_policy` 得到「是」，在代码里被当作问题来读，而不是在问题内部把意思反过来。能力参差页面指出，「真」对应「否」的 Noul 表现更差。还要注意代码没有问 Jev 什么。退款金额。金额由代码从订单记录里读取。数字本来就在能力参差的清单上。况且，记录里已经有的金额，本来就该从记录里取。

## 不该用它的地方

需要生成输出、在单个问题里做多步推理，以及数字、日期和计数，这三条文档写得很明确。其余几条是结合文档做的工程判断，看这种架构从哪里开始不再合适。

| 场合 | 为什么不合适 |
| --- | --- |
| 任何需要生成的输出 | 回复、代码、摘要、计划、解释，都在此列。文档说得很明确，用生成式模型。 |
| 开放的答案空间 | 如果你无法穷举选项，或者选项随每次请求变化，而你又无法在代码里把它们构造出来，Choice 就不合适。文档中的抽取模式绕开这一点的办法是，让正则表达式或大模型提出候选，再由 Jev 从中挑选。候选容易生成时，这招管用。 |
| 需要给出明确理由的决策 | Jev 返回的是概率，不是理由。如果监管方、客户或事故复盘需要知道为什么，理由就得来自别处，或者来自拆解本身。原子问题和权重，就是解释。 |
| 在单个问题里做多步推理 | 按设计，这类推理应当拆成多个问题，或者多次请求。如果一个决策无法拆解，它多半是系统二的任务，应交给推理模型。 |
| 数字、日期和计数 | 这些归代码管。 |
| 未经测试的语言和领域 | 英语上准确率最高。在一种数据分布上测得的校准，不会自动迁移到另一种分布上。 |

还有一些取舍来自产品，不是来自模型。Jev 出自一家年轻公司，尚处抢先体验阶段，限流规则可能不另行通知就变更。它是托管的黑盒，没有微调途径，所以模型本身只能随新版本发布而改进。不过，正如文档所述，你自己的数据仍然可以用来塑造状态和问题，或者用 Jev 的输出去训练一个下游的传统模型。别名会切换。除非固定版本，一次版本升级就可能改变一个已经校准过的系统的行为。对一个新的模型 API 来说，这些都不稀奇。但在决定是否把它放上关键路径时，这些都该算进去。

## 为什么「用 Jev 换掉大模型」没说到点子上

人们很容易把 Jev 理解成生产环境里大模型的替代品。TypeSafe 自己的文档并没有这么说。编程智能体那一页明确指出，Jev 不能直接替换编程智能体背后的模型。能力参差页面也把生成任务交还给了「其他模型」。

Jev 能取代的，是大模型的一种特定用法。被当作一个昂贵、缓慢、输出还难以解析的分类器。智能体周边的大量基础设施正是这个样子。决定用哪段提示词的路由器。判断答案有没有依据的评判器。每条消息都要跑的安全检查。循环末尾那个「任务做完了吗」的检查。其中很多之所以架在生成式模型上，是因为它是手边最方便的通用工具。不需要训练数据，也不需要另外部署一个模型。如果有一个决策模型能把这些活儿干得更快、更便宜，还附带可用的置信度信号，大模型的用途就会收窄，集中到真正需要生成和长链推理的地方。

由此可以得出一种分工。

| 谁 | 做什么 |
| --- | --- |
| 大模型 | 提议、推理、规划和写作。开放式的工作归它。 |
| Jev | 回答有界问题。哪一个，多少，是否。答案空间已知的决策归它。 |
| 代码 | 掌握控制流，执行规则，做算术，产生副作用。 |
| 人 | 处理被门槛标成不确定，或者影响很大的情况。 |

这种分工有用，也有例外。有些路由决策更适合交给大模型，因为类别模糊，而且经常变化。有些更适合用普通代码，因为一个关键词或一个数据库字段就已经给出了答案，根本不需要模型。有些决策无论置信度多高都应交给人，因为自信地犯错的代价太大，不宜自动化。此外，Jev 的置信度好不好用，全看它在你的数据上校准得如何。这一点必须先测量，才能信任。

## 这对可靠的智能体意味着什么

除了速度和价格，Jev 还带着一个论点，讲可靠性从何而来。完全围绕生成式模型构建的智能体，每跑一次都要做许多小决策，用的就是它写文章的那个模型。即便有结构化输出，这些决策通常也不带经过校准的置信度信号，而且和模型正在做的其他事情混在一起。

决策层把这些决策拆了出来。每个决策都变成一个有名字的问题，有明确的答案空间，在专门构建的状态上求值，返回一个数字。代码可以对这个数字设阈值、记日志，并用标注样本来测试。模型并没有因此变得更聪明。但智能体的行为变得更容易检查了。因为少了一些地方，没有人决定交出控制权，控制权却被交给了模型。

Jev 本身能否成为这样的决策层，取决于文档目前还无法回答的几件事。独立评测。对抗性输入下的表现。价格是否稳定。以及校准在 TypeSafe 自家工作流之外，能保持多好。而这种架构模式并不依赖 Jev。有界的问题，类型化的答案，显式的置信度，再加上由代码承担后果。无论用哪种模型，这都是构建智能体的好方法。
